# وضعیت: سند مرجع اصلی پروژه

## 1. معرفی پروژه

سپهر یک پیام‌رسان سازمانی برای استفاده در شبکه داخلی سازمان است که امکان ارتباط کاربران، مدیریت گروه‌ها، ارسال پیام، فایل، پیام صوتی، اعلان‌ها و مدیریت کاربران را فراهم می‌کند.

سامانه باید بدون وابستگی به اینترنت عمومی قابل اجرا باشد و از طریق زیرساخت داخلی سازمان در دسترس کاربران قرار گیرد.

## 2. اهداف

- ایجاد پیام‌رسان داخلی سازمان
- ارتباط خصوصی و گروهی
- مدیریت کاربران و گروه‌ها
- ارسال پیام و فایل
- ارسال پیام صوتی ضبط‌شده
- پشتیبانی از کاربران آفلاین
- مدیریت اعلان‌ها
- پیام همگانی و زمان‌بندی‌شده
- مدیریت مجوزهای دقیق
- حفظ حریم خصوصی
- پشتیبانی از دسکتاپ و وب
- امکان توسعه و نگهداری بلندمدت

## 3. ظرفیت

- تعداد حساب‌های هدف اولیه: ۵۰۰ کاربر
- تعداد کاربران هم‌زمان: بر اساس آزمون بار تعیین شود.
- ظرفیت ذخیره‌سازی فایل: قابل تنظیم و وابسته به زیرساخت.
- عملکرد باید در آزمون‌های واقعی اندازه‌گیری شود.

## 4. زیرساخت

- Windows Server 2022
- SQL Server 2022
- ذخیره‌سازی فایل روی دیسک سرور یا مسیر تعیین‌شده
- شبکه داخلی
- عدم نیاز به اینترنت عمومی برای عملکرد سامانه

مشخصات سخت‌افزار پیشنهادی اولیه سرور:
- پردازنده Intel Core i5
- حداقل RAM برابر 8GB
- فضای دیسک اولیه 1TB

این مشخصات باید در آزمون بار و ظرفیت اعتبارسنجی شوند.

## 7. کاربران

کاربران از دو طریق ایجاد می‌شوند:
- ایجاد دستی
- ورود از Excel

نام کاربری هر فرد کد پرسنلی اوست.

رمز اولیه:
- برابر کد پرسنلی
- تغییر رمز در اولین ورود اجباری

رمز عبور:
- حداقل ۸ کاراکتر
- شامل حروف یا اعداد یا ترکیبی از آن‌ها
- الزام به استفاده از کاراکتر خاص وجود ندارد.

رمز عبور باید به‌صورت Hash امن ذخیره شود.

## الحاقیه اصلاح و یکپارچه‌سازی (مصوب ادامه کار)
- هر هشت سند 01 تا 08 معتبر و بخشی از بسته مرجع هستند؛ هیچ سندی حذف یا نادیده گرفته نمی‌شود.
- اولویت حل تعارض: تصمیمات صریح و قطعی کاربر؛ سپس 01 (دامنه و نیازمندی‌ها)؛ سپس 05/06/07 (قرارداد، تست و کنترل)؛ سپس 02/03/04 (طراحی تفصیلی که باید با موارد بالاتر منطبق شود)؛ و در نهایت 08 (دستور اجرای هماهنگ). هر تصمیم اصلاحی باید در Decision Log ثبت شود.
- اصطلاح نقش گروه در تمام اسناد «هماهنگ‌کننده گروه (GroupCoordinator)» است.
- رمز اولیه برابر کد پرسنلی است و فقط تا ورود نخست اعتبار دارد؛ کاربر در اولین ورود ملزم به تغییر آن است. رمز جدید حداقل 8 نویسه دارد.
- کلاینت‌ها: WPF دسکتاپ و Web؛ هر دو از API/SignalR مشترک استفاده می‌کنند. فاز وب و پنل مدیریت صریحاً در برنامه تحویل وجود دارد.
- پیام‌ها و فایل‌ها سیاست نگهداری قابل تنظیم دارند؛ فضای شخصی از حذف دوره‌ای عادی مستثنا است مگر کاربر آن را حذف کند یا سیاست مستقل فضای شخصی اعمال شود.
- ارسال فایل اجرایی به‌صورت پیش‌فرض ممنوع است و فقط با مجوز صریح مدیرکل، کنترل‌های امنیتی و سیاست قابل تنظیم امکان‌پذیر می‌شود.
- نرمال‌سازی فارسی در متن و فیلد جستجو: ي→ی و ك→ک؛ تبدیل رقم و فاصله نیمه نیز فقط در SearchNormalization و بر اساس تنظیم/قاعده مستند. رمز، توکن، شناسه و داده باینری دست‌کاری نمی‌شوند.
- هدف اولیه 500 حساب کاربری است؛ تعداد هم‌زمان و معیارهای عملکرد با آزمون بار و گزارش واقعی تعیین می‌شوند، نه ادعای بدون آزمایش.

## پیوست نهایی اصلاحات و الزام سازگاری

تمام تصمیمات یکپارچه پیوست نهایی در انتهای این سند لازم‌الاجرا است.
**Windows 7 SP1 و Windows 8.1 الزام قطعی نصب و اجرای کلاینت WPF هستند**؛ به همراه Windows 10/11.
کلاینت Desktop بر مبنای WPF و .NET Framework 4.8 انتخاب می‌شود، مگر نمونه اولیه Phase 0
سازگاری کامل تمام وابستگی‌ها را اثبات کند. استفاده از .NET 8/9/10 برای کلاینت اصلی، پشتیبانی
Windows 7/8.1 را فراهم نمی‌کند و جایگزین این الزام نیست. هیچ حذف پشتیبانی بدون تغییر رسمی مورد
تأیید کارفرما مجاز نیست. آزمون نصب/اجرا و قابلیت‌های اصلی روی Windows 7 SP1 و 8.1 شرط پذیرش است.

این پیوست بر متن قبلی سند اولویت دارد و تمام اسناد 01 تا 08 باید با آن هماهنگ باشند.
مبنای پروژه فقط نیازمندی‌ها، تصمیم‌ها و تأییدهای روند جاری سپهر است. نسخه 4.8-Lite و
هر سند، کد، تصمیم یا طراحی مشتق از آن صریحاً خارج از مبنا است و نباید استفاده یا اقتباس شود.

1) اولویت اسناد و حل تعارض: تصمیم صریح کاربر؛ سپس 01 (نیازمندی‌ها)؛ سپس 05، 06، 07
(قراردادها، آزمون و کنترل)؛ سپس 02، 03، 04 (طراحی تفصیلی)؛ سپس 08 (دستور اجرا).
هر تغییر با شناسه، علت، اثر بر سند/API/DB/UI/تست و وضعیت در Decision Log ثبت شود.
تمام 8 سند معتبرند؛ اسناد 02، 03 و 04 حذف یا به هوش مصنوعی واگذار نشده‌اند.

2) نقش واحد گروه: «هماهنگ‌کننده گروه» با کد GroupCoordinator. نقش‌ها و مجوزهای سراسری
و گروهی دارای Scope جدا هستند. کاربر بدون عضویت گروه، نقش گروهی ندارد. عضویت/مجوز به زیرگروه
ارث نمی‌رسد. کاربر می‌تواند عضو چند گروه باشد و نقش او در هر گروه مستقل است.

3) رمز اولیه: نام کاربری و رمز اولیه کد پرسنلی است؛ رمز اولیه فقط برای ورود نخست مجاز است،
تغییر رمز در اولین ورود اجباری است و رمز جدید حداقل 8 نویسه دارد. رمز اولیه کوتاه‌تر از 8
نویسه، فقط در حالت MustChangePassword پذیرفته می‌شود. رمزها با الگوریتم هش امن ذخیره شوند.

4) کلاینت‌ها و دامنه: کلاینت WPF دسکتاپ و کلاینت Web هر دو الزامی‌اند؛ پنل مدیریت Web
در دامنه Web قرار دارد. هر دو فقط از API/SignalR مشترک استفاده می‌کنند؛ اتصال مستقیم SQL ممنوع.
فاز Web و Desktop باید در کنترل پروژه، تست و تحویل نهایی مستقل و قابل ردیابی باشند.

5) الزام قطعی سیستم‌عامل کلاینت: نصب و اجرای کلاینت اصلی WPF روی Windows 7 SP1 و Windows
8.1 الزامی است و این الزام قابل حذف یا تبدیل به «پیشنهادی» نیست. همچنین Windows 10 و 11
پشتیبانی می‌شوند. نسخه‌های 32 و 64 بیتی هر سیستم، در صورت وجود نسخه مربوط، در ماتریس آزمون
قرار گیرند. برای کلاینت Desktop فناوری سازگار انتخاب شود؛ مسیر پایه WPF روی .NET Framework 4.8
است. انتخاب هر کتابخانه، Runtime، TLS، SignalR Client، کنترل‌های UI، نصب‌کننده یا وابستگی باید
با Windows 7 SP1 و 8.1 اثبات شود. استفاده از .NET 8/9/10 برای کلاینت Desktop به‌عنوان جایگزین
سازگار با Win7/8.1 مجاز نیست. Contracts/Shared در صورت نیاز چندهدفه (از جمله netstandard2.0)
شوند. Backend می‌تواند Runtime جدید و پشتیبانی‌شده داشته باشد و الزام Win7/8.1 به سرور تعمیم ندارد.
هیچ قابلیت یا پشتیبانی این دو سیستم‌عامل با تصمیم خودکار مجری حذف نشود.

6) معیار Windows Legacy: در Phase 0 نمونه واقعی نصب/اجرا و تست اتصال HTTPS/TLS، ورود، تغییر
رمز، REST، SignalR، پیام، فایل، پیام صوتی، جست‌وجو، Sync، اعلان و reconnect روی Windows 7 SP1
و Windows 8.1 انجام شود؛ روی نسخه‌های 32/64 بیت که در ماتریس هدف‌اند. آزمون VM/ماشین واقعی،
نسخه OS، Runtime، پیش‌نیازها، نتیجه و شواهد ثبت شود. اگر تست در محیط مجری ممکن نیست، وضعیت
Blocked/NotRun ثبت و اجرای آن روی Windows واقعی شرط عبور از Phase 0 و پذیرش نهایی باشد؛ نه Passed.

7) HTTP/HTTPS: Web برای ضبط صوت، Notification و Service Worker در محیط سازمان با HTTPS و
گواهی داخلی معتبر اجرا شود. HTTP فقط برای توسعه/آزمایش محدود و بدون ادعای پشتیبانی این قابلیت‌ها.
Desktop نیز در محیط نهایی HTTPS را ترجیح دهد و TLS سازگار با سیستم‌عامل‌های Legacy در آزمون واقعی
تعیین شود.

8) مجوزها و حریم خصوصی: مدیرکل، مدیر گروه و هماهنگ‌کننده حق مشاهده محتوای گفتگوی خصوصی
دیگران یا فضای شخصی دیگران را از نقش مدیریتی دریافت نمی‌کنند. گفتگوی گروهی فقط برای اعضای مجاز
قابل خواندن است؛ عضویت جدید به‌طور پیش‌فرض تاریخچه قبل از عضویت را نمایش نمی‌دهد؛ گفتگوهای
زیرگروه مستقل‌اند. این کنترل در API و تست دسترسی اعمال شود، نه فقط UI.

9) پیام: MessageType شامل Text، File، Voice، Sticker، GIF و Announcement (در صورت فعال بودن
قابلیت) با قرارداد واحد باشد. Conversation دارای نوع Private/Group/Personal و GroupId روشن برای
گفتگوی گروهی باشد. ویرایش/حذف پیام فقط مالک در بازه پیش‌فرض 5 دقیقه یا نقش مجاز با ثبت Audit؛
حذف برای همه با مجوز و ثبت رویداد.

10) گروه/زیرگروه: حداکثر عمق پیش‌فرض 3 سطح؛ تنظیم فقط با ثبت تصمیم. چرخه، اتصال والد به
خود، و حلقه در ساختار گروه ممنوع. عضویت و مجوز مستقل و گفتگوهای زیرگروه جدا هستند.

11) فایل اجرایی: ممنوع به‌صورت پیش‌فرض. مدیرکل می‌تواند سیاست سراسری را فعال کند و مجوز ارسال
صریح به کاربر/گروه مجاز بدهد؛ فعال‌سازی بدون بررسی امنیتی به معنی مجاز شدن خودکار نیست. پسوند،
MIME، Magic Bytes، اندازه، ACL، نام ذخیره تصادفی و اسکن بدافزار بررسی شود. فایل قرنطینه تا
پایان بررسی در دسترس دانلود نیست.

12) نگهداری: Retention پیام‌ها و فایل‌های گفتگو با تنظیم جداگانه و مقدار پیش‌فرض 30 روز، قابل
تنظیم توسط مدیرکل است. فضای شخصی از حذف دوره‌ای گفتگو مستثنا است و فقط با حذف مالک یا سیاست
مستقل فضای شخصی پاک می‌شود. فایل و پیام ExpireAt یکسان بدون قواعد استثنا پذیرفته نیست.

13) فارسی و جستجو: متن اصلی پیام/نام/محتوا بدون تغییر غیرضروری نگهداری شود؛ SearchNormalization
در ستون/فیلد جدا انجام شود: ي→ی، ك→ک؛ ارقام فارسی/عربی/لاتین، اعراب و نیم‌فاصله فقط طبق
قاعده مستند برای جستجو. رمز، توکن، شناسه فنی و Binary هرگز نرمال‌سازی نشوند.

14) پیش‌فرض‌های امنیتی و نشست (قابل تنظیم و ثبت): نشست 30 دقیقه عدم فعالیت و سقف 12 ساعت؛
5 تلاش ناموفق در 15 دقیقه موجب قفل موقت 15 دقیقه؛ Rate Limit بر اساس IP/حساب/عملیات؛ توکن
Opaque تصادفی با حداقل 256 بیت entropy، فقط Hash در DB، ابطال نشست و انقضا؛ احراز SignalR
از همان نشست و عضویت/مجوز. اعداد در تنظیمات و تست قابل تغییرند.

15) صوت: فرمت مشترک و قابل پخش در Web/Desktop با codec/container توافق‌شده و آزمون سازگاری؛
حداکثر مدت پیش‌فرض 3 دقیقه، قابل تنظیم. Web فقط در Secure Context (HTTPS) ضبط کند.

16) Excel Import: قالب مستند شامل PersonnelCode، FullName و فیلدهای مجاز؛ سقف پیش‌فرض
5000 ردیف؛ PersonnelCode کلید تطبیق. کد تکراری در فایل رد و گزارش می‌شود. Import مجدد به‌روزرسانی
فیلدهای پروفایل مجاز کاربر موجود می‌کند، اما رمز، نقش، عضویت، مجوز و وضعیت امنیتی را تغییر
نمی‌دهد؛ نتیجه و خطاهای هر ردیف در ImportLog ثبت شود. کتابخانه با مجوز سازگار انتخاب شود.

17) عملکرد: هدف ظرفیت 500 حساب ثبت‌شده؛ هدف اولیه تست بار 100 کاربر هم‌زمان و تست افزایشی
تا 200 کاربر هم‌زمان (یا بیشتر در صورت نیاز)؛ اعداد latency/throughput با آزمون LAN ثبت شوند.
هدف اولیه p95 پاسخ APIهای معمول ≤2 ثانیه و تحویل پیام لحظه‌ای ≤2 ثانیه در بار تعریف‌شده است؛
این هدف‌ها معیار آزمون‌اند و بدون شاهد اجرای واقعی Passed اعلام نشوند.

18) اعلان Desktop: حالت Tray، Minimize، Toast/notification و گزینه اجرای خودکار هنگام ورود کاربر
با تنظیم قابل کنترل. رفتار برنامه بسته‌شده/خروج کامل از Tray به‌صورت روشن تعریف و تست شود.

19) Bootstrap و راه‌اندازی: Wizard اولین اجرا برای تنظیم اتصال SQL (Server/Instance/Port/Database/
Authentication)، Test Connection، ذخیره محرمانه تنظیمات و ایجاد اولین مدیرکل با مسیر امن/یک‌بار مصرف؛
عدم وجود حساب پیش‌فرض ناامن. ایجاد مدیرکل و تغییر رمز در Audit ثبت شود.

20) SQL Server: توسعه SQL Server Developer؛ تولید SQL Server Standard یا نسخه دارای SQL Server
Agent مورد تأیید سازمان. Express برای تولید و Backup زمان‌بندی‌شده مبتنی بر Agent پذیرفته نیست.
Collation فارسی/Unicode در Phase 0 با داده واقعی انتخاب و ثبت شود. Backup/Restore دستی مدیر با
SQL Server Agent طبق نیاز کاربر؛ سپهر ابزار Backup/Restore داخلی یا زمان‌بندی مستقل ندارد.

21) Hosting: مسیر پایه IIS + ASP.NET Core Hosting Bundle + WebSocket فعال، یا Windows Service/Kestrel
فقط پس از ثبت تصمیم و تست؛ HTTPS با گواهی داخلی در Web. Token، Refresh/Revocation و Hub path/event
در قرارداد 05 و پیاده‌سازی نهایی هم‌خوان باشد.

22) Sync: Cursor مستقل از IDENTITY و مبتنی بر ثبت تغییرات پایدار/Transactional Outbox؛ پوشش پیام،
ویرایش، حذف، Receipt، عضویت، مجوز و اعلان. ترتیب commit تضمین و تست شود. Receipt گروهی با
LastReadMessageId/Watermark و ثبت تنبل، نه الزاماً ردیف برای هر پیام-عضو.

23) API/DB: اعلان زمان‌بندی/ارسال، Sticker/GIF، Personal Space، Contacts، Import Logs، Retention،
Conversation.GroupId، Announcement MessageType، Subgroups و مسیرهای آن‌ها در DB/API با قرارداد واحد
تکمیل شوند. OpenAPI و تست authorization برای همه Endpointها.

24) تست: وضعیت‌های یگانه NotRun، Passed، Failed، Blocked، Deferred. تست واقعی و شاهد لازم است.
تست معماری، Integration DB، API، امنیت، بار، Regression، قطع شبکه، نصب/ارتقا/حذف و بازیابی
در برنامه باشد. Failed باز در قابلیت حیاتی مانع پذیرش؛ Blocked/Deferred با علت و ریسک.

25) تحویل: سورس کامل، Solution، Build واقعی، تست‌ها، Migration، API/OpenAPI، Installer آفلاین،
کلاینت WPF و Web، راهنمای نصب/مدیریت/کاربر، گزارش امنیت و بار، Known Issues و شواهد آزمون.

این پیوست همه موارد گزارش بازبینی (C1-C10، A1-A12، T1-T14 و پیشنهادهای P1-P12) را
به‌عنوان تصمیم اجرایی پوشش می‌دهد. اگر قابلیت/وابستگی در محیط آزمایش قابل بررسی نیست، به‌عنوان
Blocked/NotRun گزارش شود؛ رفع مستندی بدون آزمون عملی، رفع فنی محسوب نمی‌شود.


======================================================================
الزام اجرای خودکار، بدون توقف و بدون درخواست گزارش مرحله‌ای از کارفرما
======================================================================
این الحاقیه برای تمام اسناد 01 تا 08 الزام‌آور است و در صورت تعارض با عبارت‌هایی مانند «پس از گزارش، منتظر تأیید بمان»، بر آن عبارت‌ها اولویت دارد.
1. پروژه را از ابتدا تا انتها خودکار پیش ببر. فازها مراحل داخلی‌اند، نه نقاط توقف برای تأیید کارفرما.
2. گزارش پیشرفت، تصمیمات، تست‌ها، خطاها و فایل‌های هر فاز را در سوابق داخلی ثبت کن؛ گزارش مرحله‌ای برای کارفرما ارسال نکن و منتظر پاسخ نمان.
3. پس از ثبت نتیجه فاز، بی‌درنگ فاز بعد را آغاز کن و تا تکمیل کل پروژه، بسته نصب و تحویل نهایی ادامه بده.
4. تصمیم‌های فنی معمول، جزئی و قابل بازگشت را بدون پرسش با بهترین گزینه امن، پایدار و قابل نگهداری بگیر و Decision Log ثبت کن.
5. فقط اگر ادامه کار واقعاً به دسترسی/اطلاعات/مجوزی که فقط کارفرما می‌تواند فراهم کند وابسته است یا اقدام خطرناک/برگشت‌ناپذیر نیازمند رضایت است، درخواست محدود مطرح کن. کارهای مستقل را ادامه بده و کل پروژه را متوقف نکن.
6. اگر ابزار، محیط، OS، شبکه، SDK، SQL Server یا VM موجود نیست، تست‌های ممکن، تحلیل استاتیک و راهکار جایگزین را اجرا کن؛ محدودیت را ثبت کن و هرگز تست انجام‌نشده را Passed اعلام نکن. سپس سایر فازها را ادامه بده.
7. قابلیت مصوب را حذف یا به Placeholder، TODO، NotImplemented، Mock محصول یا ظاهر نمایشی تبدیل نکن. موانع حل‌ناشدنی را مستند کن و کارهای دیگر را تکمیل کن.
8. پس از هر تغییر تست مرتبط را اجرا، خطا را اصلاح و تست را تکرار کن. پیش از تحویل Clean Build، تست خودکار، بررسی امنیت/وابستگی، نصب و ارتقا را تا حد امکان انجام بده.
9. Windows 7 SP1 و Windows 8.1 الزام قطعی کلاینت WPF هستند؛ حذف، تنزل یا تبدیل به نسخه Legacy جدا بدون تأیید رسمی ممنوع است. انتخاب فناوری، پکیج، TLS، SignalR، UI و Installer باید سازگار باشد. تست OS واقعی/VM اگر در محیط مجری ممکن نیست Blocked/NotRun ثبت شود، اما توسعه ادامه یابد.
10. پروژه، سورس، Solution، migrations/schema، اسکریپت‌ها، تنظیمات نمونه بدون Secret، Desktop و Web، Installer/استقرار، تست‌ها و راهنماها را در workspace بساز و بسته ZIP نهایی را بررسی کن.
11. پایان کار فقط با تحویل سورس کامل و قابل Build، خروجی نصب/استقرار، مستندات، گزارش تست با وضعیت واقعی و Known Issues است. در پایان فقط گزارش خلاصه نهایی و لینک فایل را ارائه کن؛ گزارش‌های فازبه‌فاز و تأییدهای معمول از کارفرما نخواه.
12. نسخه 4.8-Lite و هر محتوای مشتق از آن مطلقاً خارج از مبناست.
معیار پایان: تمام کارهای قابل انجام تکمیل، بسته نهایی صحت‌سنجی و فقط موانع بیرونی و تست‌های Blocked/NotRun شفاف اعلام شده باشند.


======================================================================
الزام ادامه‌پذیری پروژه پس از محدودیت زمان، حجم، توکن یا قطع جلسه
======================================================================
این پروتکل مکمل اجرای خودکار است و باید بدون نیاز به حافظه چت قبلی قابل اجرا باشد.

1) فایل checkpoint مرکزی با نام PROJECT_RESUME_STATE.md را در ریشه workspace پروژه ایجاد کن و در طول کار نگه دار. همچنین فایل RESUME_AI_INSTRUCTIONS.txt را برای دستور شروع مجدد ایجاد/به‌روز کن. این دو فایل جزو تحویل پروژه باشند.
2) در پایان هر کار معنادار، و پیش از پایان احتمالی محدودیت پاسخ/زمان/توکن، وضعیت را در checkpoint ثبت و ذخیره کن؛ منتظر درخواست کارفرما نباش. در صورت امکان از Git commitهای کوچک و توصیفی استفاده کن؛ اما Git جای checkpoint را نمی‌گیرد.
3) checkpoint باید حداقل شامل این موارد باشد: شناسه/تاریخ آخرین به‌روزرسانی؛ هدف کلی و قواعد غیرقابل‌تغییر؛ مرحله و زیرمرحله فعلی؛ کارهای کامل‌شده و شواهد؛ کارهای در حال انجام و نیمه‌تمام با وضعیت دقیق؛ فهرست فایل‌های ایجاد/تغییر؛ آخرین Build/Test و فرمان دقیق، نتیجه و وضعیت Passed/Failed/Blocked/NotRun؛ خطاهای باقی‌مانده؛ تصمیم‌های فنی و دلیل؛ موانع/وابستگی‌ها؛ و فهرست گام‌های بعدی به ترتیب اولویت.
4) وضعیت checkpoint را صادقانه و دقیق ثبت کن. چیزی که اجرا یا بررسی نشده Completed/Passed نیست. برای کارهای نیمه‌تمام، آخرین نقطه امن و روش ادامه را مشخص کن.
5) اگر جلسه، زمینه گفتگو، طول پاسخ، توکن، زمان اجرا یا دسترسی ابزار به پایان رسید، قبل از توقف checkpoint را به‌روز کن. اگر توقف ناگهانی بود، در جلسه بعد ابتدا workspace و checkpoint را با فایل‌های واقعی، Git و خروجی‌های Build/Test تطبیق بده؛ checkpoint را کورکورانه فرض حقیقت نکن.
6) پس از رفع محدودیت، کارفرما لازم نیست شرح پیشرفت یا پاسخ‌های قبلی را دوباره ارائه کند. کافی است workspace/فایل‌های پروژه و اسناد 01 تا 08 را در دسترس عامل جدید قرار دهد و متن RESUME_AI_INSTRUCTIONS.txt را ارسال کند. اگر checkpoint در دسترس نبود، عامل باید با بررسی فایل‌ها و Git وضعیت را بازسازی کند و فقط در صورت وجود مانع واقعیِ وابسته به کارفرما سؤال محدود بپرسد.
7) عامل شروع مجدد باید ابتدا اسناد 01 تا 08 را بخواند، قواعد قطعی را استخراج کند، checkpoint را بررسی کند، وضعیت واقعی پروژه را اعتبارسنجی کند، کار نیمه‌تمام را شناسایی کند و از همان نقطه ادامه دهد؛ از ابتدا بازسازی یا تکرار کارهای سالم نکند مگر برای اعتبارسنجی، رفع خطا یا بهبود لازم.
8) پس از بازخوانی وضعیت، بلافاصله به اجرای کار ادامه بده؛ گزارش مرحله‌ای برای کارفرما نده و برای ادامه تأیید نخواه. سوابق و گزارش‌های داخلی را checkpoint و فایل‌های پروژه به‌روزرسانی کن.
9) checkpoint باید کوتاه، ساختاریافته، خوانا و مستقل از مدل/پلتفرم هوش مصنوعی باشد. مسیرها نسبی به ریشه پروژه باشند؛ هیچ رمز، Token، کلید، رشته اتصال حاوی Secret یا داده شخصی واقعی در checkpoint ذخیره نشود.
10) در هر به‌روزرسانی checkpoint، بخش «NEXT ACTIONS» با حداکثر 10 اقدام مشخص و اجرایی به ترتیب اولویت نوشته شود و نخستین اقدام بعدی دقیقاً قابل انجام باشد.
11) اگر کار در چند محیط/هوش مصنوعی ادامه می‌یابد، تمام فایل‌های تغییر یافته، checkpoint، دستور شروع مجدد، مستندات و در صورت امکان commit/patch باید در بسته قابل انتقال باشند. به حافظه داخلی یک هوش مصنوعی یا سابقه یک چت وابسته نباش.
12) این پروتکل، الزام اجرای خودکار و عدم درخواست گزارش/تأیید مرحله‌ای را تغییر نمی‌دهد؛ هدف آن فقط حفظ پیشرفت و ادامه بدون وقفه پس از محدودیت است.

الگوی پیشنهادی checkpoint:
- PROJECT / NON-NEGOTIABLE RULES
- LAST VERIFIED CHECKPOINT
- CURRENT PHASE / SUBTASK
- COMPLETED (with file paths and evidence)
- IN PROGRESS / PARTIAL (exact state)
- FILES CHANGED
- BUILD / TEST STATUS (commands, results, statuses)
- OPEN ISSUES / BLOCKERS
- DECISIONS MADE
- NEXT ACTIONS (ordered, concrete)
- RESUME COMMAND

متن شروع مجدد باید عامل را به بازبینی وضعیت و ادامه کار ملزم کند، نه ارائه گزارش یا درخواست تأیید.
